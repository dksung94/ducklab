# 0001 · ducklab 요구사항 분석

> 상태: 초안 (2026-09-10) · 이 문서는 무엇을 만들 것인가와 왜를 정한다. 구현 결정은
> 이 문서와 충돌하면 문서를 먼저 고친다.

## 1. 한 줄 정의

`.py` 파일을 **주피터처럼 셀 단위로 라이브 렌더**하되, 소스는 순수 `.py`로 두고,
**AI(Claude Code)와 사람이 같은 파일 위에서 페어**하며, 웹에서 편집·실행·터미널까지
되는 **로컬 반응형 리서치 환경**.

## 2. 동기 — 기존 도구의 통증

- **Jupyter/`.ipynb`**: 파일이 JSON이라 git·AI 편집·파일 관리가 불편. 셀 실행순서 상태가
  숨어 재현성이 깨짐. Jupyter MCP는 파일 관리·연동이 번거로움.
- **marimo**: 반응형·`.py`는 좋으나 구독 서비스가 아니고 Claude Code 연동이 없음.
- **구독형(Deepnote/Hex/Datalore/Colab)**: 실시간 협업·AI는 되나 **AI가 Claude가 아니고**,
  데이터를 클라우드로 올려야 함(로컬 `/live/share/data` 마찰).
- **code-server(브라우저 VS Code)**: 요구의 90%를 충족하나 "AI가 파일을 편집하면
  자동 렌더"가 아니라 매번 셀을 수동 실행해야 함.

→ 비어 있는 자리: **로컬 + Claude 네이티브 + `.py` 소스 + 반응형(파일 저장 시 자동 반영) +
파일당 격리 + 웹 편집/터미널.** 그게 ducklab.

## 3. 사용자·시나리오

- **S1 · AI 단독**: Claude Code가 `.py`를 편집/셀 실행 → 브라우저에 결과가 라이브로 쌓임.
  사람은 브라우저만 열어두고 관찰.
- **S2 · 페어**: 사람이 웹 에디터/터미널에서 손대고, AI가 같은 파일을 편집. 양쪽 변경이
  서로에게 실시간 반영.
- **S3 · 여러 분석 병행**: 파일당 1분석. 여러 `.py`를 열어 각자 독립 상태로 돌림.

## 4. 요구사항

### Must
1. **소스 = 순수 `.py`** (git 친화, AI가 텍스트로 편집). 노트북 전용 포맷 없음.
2. **셀 렌더링**: `.py`를 셀 단위로 표시(코드 + 출력: 텍스트·표·그림·에러).
3. **반응형 (디스크→웹)**: 파일이 바뀌면 **새로고침 없이** 셀 재파싱·갱신.
4. **웹 편집 (웹→디스크)**: 브라우저에서 수정하면 `.py`로 저장(양방향).
5. **파일당 커널 1개**: 파일=1분석은 독립 네임스페이스. 파일 내부 셀은 그 커널 공유.
6. **AI 연동**: Claude Code가 `.py`를 편집/실행하는 것이 곧 연동(파일 기반). 특수 API 불필요.
7. **로컬 실행**: 데이터(`/live/share/data` 등) 그대로 접근, 클라우드 업로드 없음.

### Should
8. **웹 터미널**: xterm 기반 실제 셸을 임베드 — 거기서 바로 코딩/명령/Claude Code 실행.
9. **명시적 실행 모델**: 저장마다 자동실행하지 않음(부작용·무한루프 방지). 셀/전체 실행은
   버튼·단축키, 또는 AI 트리거.
10. **커널 수명관리**: 열린/최근 파일만 커널 유지, idle 타임아웃·닫기 시 종료.
11. **출력 지속**: 마지막 실행 출력을 `.py` 옆 사이드카(예: `.ipynb`/`.json`/`_outputs/`)에
    저장해 새 세션에서 복원(선택).
12. **원격/모바일 접속**: Tailscale 경유로 폰·외부 기기에서 접속(관찰·간단 편집). 보안
    전제는 §5.7 — Tailscale `serve`(≠`funnel`) + 앱 인증 + Origin 검증이 켤 때 Must.

### Could
13. 실시간 다중 커서 협업(여러 사람 동시 편집).
14. 변수 탐색기·실행 히스토리·프로파일.
15. 셀 의존 그래프 기반 반응형 재실행(marimo식) — 기본은 명시 실행.

### Won't (초기)
- 클라우드 호스팅/멀티테넌시.
- 노트북 전용 바이너리 포맷.
- 판정/평가에 LLM 삽입(이건 실행 환경일 뿐).

## 5. 핵심 설계 결정

### 5.1 셀 = `# %%` percent format
`.py`를 `# %%` 구분자로 나눈 영역 하나 = 셀 하나. VS Code·Spyder·jupytext 표준과 호환.
파일은 여전히 순수 `.py`. 셀 id = 순서 + 내용 해시(안정 매칭용).
```python
# %%
df = load(...)
# %%
df.plot()
```

### 5.2 커널: **파일당 하나** (전역 공유 아님)
- 파일=1분석이므로 각 파일은 독립 커널 → 교차 변수 누출 없음 = **재현성**.
- 파일 내부 셀들은 그 한 커널을 공유(Jupyter식 누적 상태).
- 주피터의 "노트북1=커널1"을 "`.py`1=커널1"로.
- 재로드 비용 우려는 **디스크 캐시**(parquet 등, 초 단위)로 상쇄 — 격리가 사실상 공짜.
  진짜 대용량 공유가 병목이면 그때만 "데이터 보관 프로세스 + 커널 접속" fallback.

### 5.3 셀 ↔ 커널 매칭
바닥부터 커널을 만들지 않고 **Jupyter 프로토콜 재사용**(`jupyter_client`). 셀 실행 =
그 영역 코드를 커널에 `execute_request`로 전송. 커널이 돌려주는 `stream`·`execute_result`·
`display_data`·`error`가 요청의 `msg_id`에 태그돼 오므로, **msg_id → 셀 id**로 매핑해
해당 셀 아래 렌더. (코드영역 ↔ 실행요청 ↔ 출력이 1:1.)

### 5.4 반응형·양방향
- 디스크→웹: 파일워치(watchfiles) → 셀 재파싱 → 웹소켓 push.
- 웹→디스크: 에디터 변경 → 디바운스 후 `.py` 저장.
- 충돌: 마지막-writer + 디바운스로 단순화(초기). 실행은 상태를 바꾸므로 **명시 트리거만**.

### 5.5 웹 터미널
xterm.js(프론트) + pty(백엔드, `ptyprocess`)를 웹소켓 연결 → 진짜 셸. 여기서 Claude Code·
명령 실행.

### 5.6 AI 연동
Claude Code가 `.py`를 파일로 편집 = 연동. 파일워치가 웹에 반영. 선택적으로 "AI가 셀/전체
실행" HTTP 엔드포인트 추가(예: `POST /run {file, cell}`).

## 5.7 원격 접속 · 보안 (모바일)

ducklab은 웹 터미널(pty) + 커널 = **사실상 원격 코드 실행(RCE)**이다. 접근 통제 = 호스트
셸 통제이므로 원격(특히 모바일) 접속은 다음 전제하에서만.

- **네트워크: Tailscale `serve` 전용.** WireGuard 암호화 + 내 tailnet 기기만. **`funnel`
  (공개 인터넷 노출)은 금지** — RCE 서비스라 치명적.
- **바인딩: `0.0.0.0` 금지.** `localhost`(+ Serve 프록시) 또는 tailnet IP만. LAN·타
  인터페이스 노출 차단.
- **앱 레벨 인증 필수(토큰/패스워드)** — tailnet 뒤에서도(기기 탈취·tailnet 공유 대비).
- **Tailscale ACL**로 호스트/포트를 내 기기만 닿게 제한.
- **WebSocket Origin 검증 + CSRF/DNS-rebinding 방어** — tailnet 기기 브라우저의 악성
  사이트 drive-by 차단.
- **기기 보안**: 모바일 = 머신 셸 → 화면잠금/생체인증. 서버는 사용 시에만 기동.

요구 등급: 원격/모바일 접속은 **Should**, 위 보안 항목은 그 접속을 켤 때 **Must**.

## 6. 아키텍처 (초안)

```
브라우저 (SPA)
 ├─ 에디터        CodeMirror — .py 편집, # %% 셀 경계 표시
 ├─ 셀 렌더러      셀별 코드+출력(text/table/img/error) 렌더
 └─ 터미널        xterm.js
        │  websocket (편집·실행·출력·터미널 스트림)
        ▼
서버 (Python · FastAPI)
 ├─ FileStore     .py 읽기/쓰기 + watchfiles(디스크→웹 push)
 ├─ CellParser    .py ↔ 셀 목록(# %% 파싱, 셀 id)
 ├─ KernelHub     파일당 jupyter_client 커널 관리(수명·라우팅)
 │                 execute_request → msg_id → 셀 매핑 → 출력 스트림
 └─ PtyBridge     pty ↔ 터미널 웹소켓
```
- 서버는 로컬 프로세스 하나. `duck lab <dir>` 로 기동, 브라우저로 접속.

## 7. 열린 질문

- 출력 지속 포맷: 사이드카 `.ipynb`(jupytext 호환) vs 자체 `_outputs/`?
- 반응형의 범위: 렌더만 자동 vs 실행까지 자동(marimo식 의존그래프)? → 기본 렌더 자동, 실행 명시.
- 웹 에디터 vs 로컬 에디터(VS Code) 병행 시 양방향 동기화 경계.
- 다중 사용자 협업(Could)을 언제 넣을지.

## 8. 로드맵

```
M0  최소 프로토타입   파일당 커널 + # %% 셀 실행 + 출력 렌더 + 파일워치 반응형 (단일 파일)
M1  웹 편집·터미널     CodeMirror 양방향 저장 + xterm/pty
M2  다파일·수명관리     파일 탐색 + 파일당 커널 라우팅 + idle 종료 + 출력 지속
M3  AI 트리거·페어      run 엔드포인트, 편집 충돌 처리, (선택) 다중커서 협업
```

## 9. 기술 후보

- 백엔드: Python + FastAPI, `jupyter_client`(커널), `watchfiles`(파일워치), `ptyprocess`(pty).
- 프론트: CodeMirror 6(에디터), xterm.js(터미널), 경량 렌더러(표·img·ansi).
- 배포: 단일 CLI `duck lab` (pip 설치), 로컬 셀프호스트.
